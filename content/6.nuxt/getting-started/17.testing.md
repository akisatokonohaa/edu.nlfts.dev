Nuxt memberikan dukungan utama (*first-class support*) untuk pengujian *end-to-end* dan *unit* pada aplikasi kamu melalui `@nuxt/test-utils`. Ini adalah sekumpulan utilitas dan konfigurasi pengujian yang saat ini juga menjadi pondasi bagi [pengujian yang kami gunakan pada Nuxt itu sendiri](https://github.com/nuxt/nuxt/tree/main/test) serta pengujian di seluruh ekosistem *module*.

## Instalasi

Supaya kamu bisa mengelola dependensi pengujian lainnya dengan leluasa, `@nuxt/test-utils` hadir dengan berbagai *peer dependency* opsional. Sebagai contoh:

- Kamu bisa memilih antara `happy-dom` atau `jsdom` untuk lingkungan *runtime* Nuxt
- Kamu bisa memilih antara `vitest`, `cucumber`, `jest`, atau `playwright` untuk *runner* pengujian *end-to-end*
- `playwright-core` hanya dibutuhkan kalau kamu ingin menggunakan utilitas pengujian *browser* bawaan (dan tidak menggunakan `@playwright/test` sebagai *runner* pengujian kamu)

::code-group{sync="pm"}
```bash [npm]
npm i --save-dev @nuxt/test-utils vitest @vue/test-utils happy-dom playwright-core
```
```bash [yarn]
yarn add --dev @nuxt/test-utils vitest @vue/test-utils happy-dom playwright-core
```
```bash [pnpm]
pnpm add -D @nuxt/test-utils vitest @vue/test-utils happy-dom playwright-core
```
```bash [bun]
bun add --dev @nuxt/test-utils vitest @vue/test-utils happy-dom playwright-core
```
::

## Pengujian Unit (*Unit Testing*)

Saat ini, kami menyediakan lingkungan untuk menguji kode yang membutuhkan lingkungan *runtime* [Nuxt](https://nuxt.com). Untuk sekarang, _hanya mendukung `vitest`_ (meskipun kontribusi untuk menambahkan *runtime* lain sangat kami apresiasi).

### Pengaturan

1. Tambahkan `@nuxt/test-utils/module` ke file `nuxt.config` kamu (opsional). Ini akan menambahkan integrasi Vitest ke dalam Nuxt DevTools milikmu, yang mendukung eksekusi pengujian unit langsung saat *development*.

   ```ts twoslash
   export default defineNuxtConfig({
     modules: [
       '@nuxt/test-utils/module',
     ],
   })
   ```

2. Buat sebuah file `vitest.config.ts` dengan konten berikut:

   ```ts twoslash
   import { defineConfig } from 'vitest/config'
   import { defineVitestProject } from '@nuxt/test-utils/config'

   export default defineConfig({
     test: {
       projects: [
         {
           test: {
             name: 'unit',
             include: ['test/unit/*.{test,spec}.ts'],
             environment: 'node',
           },
         },
         {
           test: {
             name: 'e2e',
             include: ['test/e2e/*.{test,spec}.ts'],
             environment: 'node',
           },
         },
         await defineVitestProject({
           test: {
             name: 'nuxt',
             include: ['test/nuxt/*.{test,spec}.ts'],
             environment: 'nuxt',
           },
         }),
       ],
     },
   })
   ```

    ::note
    `defineVitestProject` hanya ditujukan untuk pengujian di lingkungan Nuxt. Pengujian *end-to-end* sebaiknya dikonfigurasi sebagai proyek `test.environment: 'node'` yang biasa.
    ::

3. Kalau pengujian lingkungan Nuxt kamu berada di luar folder `test/nuxt/`, periksa bagian [Dukungan TypeScript dalam Pengujian](#dukungan-typescript-dalam-pengujian) untuk menambahkannya ke dalam konteks TypeScript.

::tip
Saat mengimpor `@nuxt/test-utils` di konfigurasi vitest, kamu harus memastikan ada `"type": "module"` yang dituliskan di `package.json` atau mengubah nama file konfigurasi vitest kamu dengan akhiran yang tepat.
> Contohnya, `vitest.config.m{ts,js}`.
::

::tip
Kamu bisa mengatur variabel lingkungan untuk pengujian dengan menggunakan file `.env.test`.
::

### Menggunakan Lingkungan *Runtime* Nuxt

Dengan memanfaatkan [*project Vitest*](https://vitest.dev/guide/projects.html#test-projects), kamu bisa mengendalikan secara detail pengujian mana yang berjalan di lingkungan mana:

- **Pengujian Unit**: Letakkan pengujian unit biasa di `test/unit/` — pengujian ini akan berjalan di lingkungan Node demi kecepatan
- **Pengujian Nuxt**: Letakkan pengujian yang bergantung pada lingkungan *runtime* Nuxt di `test/nuxt/` — pengujian ini akan berjalan di dalam lingkungan *runtime* Nuxt

#### Alternatif: Pengaturan Simpel

Kalau kamu lebih suka konfigurasi yang simpel dan ingin semua pengujian berjalan di lingkungan Nuxt, kamu bisa menggunakan konfigurasi dasar ini:

```ts twoslash
import { defineVitestConfig } from '@nuxt/test-utils/config'
import { fileURLToPath } from 'node:url'

export default defineVitestConfig({
  test: {
    environment: 'nuxt',
    // kamu bisa mengatur opsi lingkungan khusus Nuxt secara opsional
    // environmentOptions: {
    //   nuxt: {
    //     rootDir: fileURLToPath(new URL('./playground', import.meta.url)),
    //     domEnvironment: 'happy-dom', // 'happy-dom' (bawaan) atau 'jsdom'
    //     overrides: {
    //       // konfigurasi Nuxt lainnya yang ingin kamu masukkan
    //     }
    //   }
    // }
  },
})
```

Kalau kamu menggunakan pengaturan simpel dengan `environment: 'nuxt'` sebagai bawaan, kamu bisa menarik diri (*opt-out*) dari [lingkungan Nuxt](https://vitest.dev/guide/environment.html#test-environment) per file pengujian jika diperlukan.

```ts twoslash
// @vitest-environment node
import { test } from 'vitest'

test('pengujian saya', () => {
  // ... pengujian tanpa lingkungan Nuxt!
})
```

::warning
Cara ini tidak kami sarankan karena akan menciptakan lingkungan *hybrid* di mana *plugin* Vite Nuxt berjalan, tetapi *entry* Nuxt dan `nuxtApp` tidak diinisialisasi. Ini bisa memicu *error* yang sulit dilacak.
::

### Mengatur Struktur Pengujian

Dengan pengaturan berbasis *project*, kamu bisa menyusun pengujian seperti berikut:

```bash [Struktur direktori]
test/
├── e2e/
│   └── ssr.test.ts
├── nuxt/
│   ├── components.test.ts
│   └── composables.test.ts
├── unit/
│   └── utils.test.ts
```

Tentu saja kamu bebas memilih struktur pengujian lainnya, tapi memisahkan lingkungan *runtime* Nuxt dari pengujian *end-to-end* Nuxt itu sangat penting untuk menjaga kestabilan pengujian.

#### Dukungan TypeScript dalam Pengujian

Secara bawaan, file pengujian yang ada di dalam direktori `test/nuxt/` dan `tests/nuxt/` sudah termasuk ke dalam [konteks TypeScript aplikasi Nuxt](/docs/4.x/guide/concepts/typescript#how-nuxt-uses-project-references). Artinya, file-file tersebut akan mengenali *alias* Nuxt (seperti `~/`, `@/`, `#imports`) dan TypeScript akan memahami *auto-import* yang berfungsi di aplikasi Nuxt kamu.

::tip
Ini sesuai dengan struktur yang kami rekomendasikan, di mana hanya pengujian yang butuh lingkungan *runtime* Nuxt yang ditempatkan di direktori tersebut. Pengujian unit di direktori lain seperti `test/unit/` bisa ditambahkan secara manual kalau diperlukan.
::

##### Menambahkan direktori pengujian lainnya

Kalau kamu memiliki pengujian di direktori lain yang akan dijalankan di lingkungan Vitest Nuxt, kamu bisa memasukkannya ke dalam konteks TypeScript aplikasi Nuxt dengan menambahkannya ke konfigurasi:

<!-- @case-police-ignore tsConfig -->

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  typescript: {
    tsConfig: {
      include: [
        // jalur ini relatif terhadap file .nuxt/tsconfig.json yang dihasilkan
        '../test/other-nuxt-context/**/*',
      ],
    },
  },
})
```

::important
Pengujian unit sebaiknya tidak bergantung pada fitur *runtime* Nuxt seperti *auto-import* atau *composable*. Hanya tambahkan dukungan *alias* jalur TypeScript kalau pengujian kamu mengimpor dari file sumber (misalnya `~/utils/helpers`), bukan untuk fitur spesifik Nuxt.
::

#### Menjalankan Pengujian

Dengan pengaturan *project* ini, kamu bisa menjalankan suite pengujian yang berbeda:

```bash
# Jalankan semua pengujian
npx vitest

# Jalankan hanya pengujian unit
npx vitest --project unit

# Jalankan hanya pengujian Nuxt
npx vitest --project nuxt

# Jalankan pengujian dalam mode watch
npx vitest --watch
```

::warning
Saat kamu menjalankan pengujian di dalam lingkungan Nuxt, pengujian tersebut akan berjalan di lingkungan [`happy-dom`](https://github.com/capricorn86/happy-dom) atau [`jsdom`](https://github.com/jsdom/jsdom). Sebelum pengujian kamu dijalankan, aplikasi Nuxt global akan diinisialisasi (termasuk menjalankan *plugin* atau kode apa pun yang kamu definisikan di `app.vue`).

Ini berarti kamu harus sangat berhati-hati untuk tidak mengubah *state* global di dalam pengujian (atau, kalau memang perlu, pastikan untuk mengembalikannya ke semula setelahnya).
::

### 🎭 *Mock* Bawaan

`@nuxt/test-utils` menyediakan beberapa *mock* bawaan untuk lingkungan DOM.

#### `intersectionObserver`

Bawaannya `true`, membuat *dummy class* tanpa fungsi apa pun untuk *API* IntersectionObserver.

#### `indexedDB`

Bawaannya `false`, menggunakan [`fake-indexeddb`](https://github.com/dumbmatter/fakeIndexedDB) untuk membuat *mock* fungsional dari *API* IndexedDB.

Keduanya bisa dikonfigurasi di bagian `environmentOptions` pada file `vitest.config.ts` kamu:

```ts twoslash
import { defineVitestConfig } from '@nuxt/test-utils/config'

export default defineVitestConfig({
  test: {
    environmentOptions: {
      nuxt: {
        mock: {
          intersectionObserver: true,
          indexedDb: true,
        },
      },
    },
  },
})
```

### 🛠️ *Helpers* (Penolong)

`@nuxt/test-utils` menyediakan sejumlah *helper* untuk mempermudah pengujian aplikasi Nuxt kamu.

#### `mountSuspended`

`mountSuspended` memungkinkan kamu untuk *mount* komponen Vue apa pun di dalam lingkungan Nuxt, yang mendukung *setup* bersifat *async* dan akses terhadap *injection* dari *plugin* Nuxt kamu.

::note
Di balik layar, `mountSuspended` membungkus `mount` dari `@vue/test-utils`, jadi kamu bisa melihat [dokumentasi Vue Test Utils](https://test-utils.vuejs.org/guide/) untuk informasi lebih lanjut mengenai opsi yang bisa kamu masukkan dan cara menggunakannya.
::

Contohnya seperti ini:

```ts twoslash
// @noErrors
import { expect, it } from 'vitest'
import type { Component } from 'vue'

declare module '#components' {
  export const SomeComponent: Component
}
// ---cut---
// tests/components/SomeComponents.nuxt.spec.ts
import { mountSuspended } from '@nuxt/test-utils/runtime'
import { SomeComponent } from '#components'

it('bisa melakukan mount pada beberapa komponen', async () => {
  const component = await mountSuspended(SomeComponent)
  expect(component.text()).toMatchInlineSnapshot(
    '"Ini adalah komponen yang di-auto-import"',
  )
})
```

```ts twoslash
// @noErrors
import { expect, it } from 'vitest'
// ---cut---
// tests/components/SomeComponents.nuxt.spec.ts
import { mountSuspended } from '@nuxt/test-utils/runtime'
import App from '~/app.vue'

// tests/App.nuxt.spec.ts
it('bisa juga melakukan mount pada aplikasi', async () => {
  const component = await mountSuspended(App, { route: '/test' })
  expect(component.html()).toMatchInlineSnapshot(`
      "<div>Ini adalah komponen yang di-auto-import</div>
      <div> Saya adalah komponen global </div>
      <div>/</div>
      <a href="/test"> Tautan uji </a>"
    `)
})
```

Objek opsi ini menerima opsi *mount* dari `@vue/test-utils` serta properti berikut:

  - `route`: rute awal, atau `false` untuk melewatkan perubahan rute awal (bawaannya adalah `/`).

#### `renderSuspended`

`renderSuspended` memungkinkan kamu untuk merender komponen Vue apa pun di dalam lingkungan Nuxt menggunakan `@testing-library/vue`, yang mendukung *setup* bersifat *async* dan akses terhadap *injection* dari *plugin* Nuxt kamu.

Ini sebaiknya digunakan bersamaan dengan utilitas dari Testing Library, seperti `screen` dan `fireEvent`. Pasang [@testing-library/vue](https://testing-library.com/docs/vue-testing-library/intro/) di proyekmu untuk menggunakannya.

Selain itu, Testing Library juga bergantung pada *testing globals* untuk proses pembersihan (*cleanup*). Kamu harus mengaktifkannya di [konfigurasi Vitest](https://vitest.dev/config/globals) kamu.

Komponen yang dimasukkan akan di-render di dalam sebuah `<div id="test-wrapper"></div>`.

Contohnya:

```ts twoslash
// @noErrors
import { expect, it } from 'vitest'
import type { Component } from 'vue'

declare module '#components' {
  export const SomeComponent: Component
}
// ---cut---
// tests/components/SomeComponents.nuxt.spec.ts
import { renderSuspended } from '@nuxt/test-utils/runtime'
import { SomeComponent } from '#components'
import { screen } from '@testing-library/vue'

it('bisa merender beberapa komponen', async () => {
  await renderSuspended(SomeComponent)
  expect(screen.getByText('Ini adalah komponen yang di-auto-import')).toBeDefined()
})
```

```ts twoslash
// @noErrors
import { expect, it } from 'vitest'
// ---cut---
// tests/App.nuxt.spec.ts
import { renderSuspended } from '@nuxt/test-utils/runtime'
import App from '~/app.vue'

it('bisa juga merender aplikasi', async () => {
  const html = await renderSuspended(App, { route: '/test' })
  expect(html).toMatchInlineSnapshot(`
    "<div id="test-wrapper">
      <div>Ini adalah komponen yang di-auto-import</div>
      <div> Saya adalah komponen global </div>
      <div>Halaman Index</div><a href="/test"> Tautan uji </a>
    </div>"
  `)
})
```

Objek opsi ini menerima opsi *render* dari `@testing-library/vue` serta properti berikut:

  - `route`: rute awal, atau `false` untuk melewatkan perubahan rute awal (bawaannya adalah `/`).

#### `mockNuxtImport`

`mockNuxtImport` memungkinkan kamu untuk melakukan *mock* terhadap fungsi *auto-import* milik Nuxt. Sebagai contoh, kalau kamu ingin melakukan *mock* pada `useState`, kamu bisa melakukannya seperti ini:

```ts twoslash
import { mockNuxtImport } from '@nuxt/test-utils/runtime'

mockNuxtImport('useState', () => {
  return () => {
    return { value: 'mocked storage' }
  }
})

// pengujian kamu ada di sini
```

Kamu bisa memberikan tipe secara eksplisit pada *mock* agar lebih aman secara tipe, dan menggunakan implementasi asli yang diteruskan ke fungsi *factory* saat melakukan *mock* pada fungsi yang kompleks.

```ts twoslash [test/nuxt/import.test.ts]
import { mockNuxtImport } from '@nuxt/test-utils/runtime'

mockNuxtImport<typeof useState>('useState', (original) => {
  return (...args) => {
    return { ...original('some-key'), value: 'mocked state' }
  }
})

// atau tentukan target yang ingin di-mock
mockNuxtImport(useState, (original) => {
  return (...args) => {
    return { ...original('some-key'), value: 'mocked state' }
  }
})

// pengujian kamu ada di sini
```

::note
`mockNuxtImport` hanya bisa digunakan sekali per impor yang di-*mock* di setiap file pengujian. Ini sebenarnya adalah *macro* yang diubah menjadi `vi.mock`, dan `vi.mock` ini di-*hoist* (dinaikkan), seperti yang dijelaskan [di dokumentasi Vitest](https://vitest.dev/api/vi#vi-mock).
::

Kalau kamu perlu melakukan *mock* pada impor Nuxt dan memberikan implementasi yang berbeda di antara pengujian, kamu bisa melakukannya dengan membuat dan mengekspos *mock* menggunakan [`vi.hoisted`](https://vitest.dev/api/vi#vi-hoisted), lalu gunakan *mock* tersebut di dalam `mockNuxtImport`. Dengan begitu, kamu memiliki akses ke impor yang di-*mock*, dan bisa mengubah implementasinya di antara pengujian. Berhati-hatilah untuk [mengembalikan *mock*](https://vitest.dev/api/mock#mockrestore) sebelum atau setelah setiap pengujian untuk membatalkan perubahan *state mock* di antara eksekusi.

```ts twoslash
import { vi } from 'vitest'
import { mockNuxtImport } from '@nuxt/test-utils/runtime'

const { useStateMock } = vi.hoisted(() => {
  return {
    useStateMock: vi.fn(() => {
      return { value: 'mocked storage' }
    }),
  }
})

mockNuxtImport('useState', () => {
  return useStateMock
})

// Lalu, di dalam sebuah pengujian
useStateMock.mockImplementation(() => {
  return { value: 'sesuatu yang lain' }
})
```

Kalau kamu hanya perlu melakukan *mock* pada perilaku di dalam sebuah pengujian, kamu juga bisa menggunakan pendekatan berikut ini.

```ts twoslash
import { beforeEach, vi } from 'vitest'
import { mockNuxtImport } from '@nuxt/test-utils/runtime'

mockNuxtImport(useRoute, original => vi.fn(original))

beforeEach(() => {
  vi.resetAllMocks()
})

// Lalu, di dalam sebuah pengujian
const useRouteOriginal = vi.mocked(useRoute).getMockImplementation()!
vi.mocked(useRoute).mockImplementation(
  (...args) => ({ ...useRouteOriginal(...args), path: '/mocked' }),
)
```

#### `mockComponent`

`mockComponent` memungkinkan kamu untuk melakukan *mock* terhadap komponen Nuxt.
Argumen pertama bisa berupa nama komponen dalam format PascalCase, atau jalur relatif dari komponen tersebut.
Argumen kedua adalah fungsi *factory* yang mengembalikan komponen *mock*.

Sebagai contoh, untuk melakukan *mock* pada `MyComponent`, kamu bisa melakukannya seperti ini:

```ts twoslash
import { mockComponent } from '@nuxt/test-utils/runtime'

mockComponent('MyComponent', {
  props: {
    value: String,
  },
  setup (props) {
    // ...
  },
})

// jalur relatif atau alias juga bisa digunakan
mockComponent('~/components/my-component.vue', () => {
  // atau menggunakan fungsi factory
  return defineComponent({
    setup (props) {
      // ...
    },
  })
})

// atau kamu bisa menggunakan SFC untuk mengalihkan ke komponen mock
mockComponent('MyComponent', () => import('./MockComponent.vue'))

// pengujian kamu ada di sini
```

> **Catatan**: Kamu tidak bisa merujuk ke variabel lokal di dalam fungsi *factory* karena kodenya akan di-*hoist* (dinaikkan). Kalau kamu perlu mengakses *API* Vue atau variabel lainnya, kamu harus mengimpornya langsung di dalam fungsi *factory* tersebut.

```ts twoslash
import { mockComponent } from '@nuxt/test-utils/runtime'

mockComponent('MyComponent', async () => {
  const { ref, h } = await import('vue')

  return defineComponent({
    setup (props) {
      const counter = ref(0)
      return () => h('div', null, counter.value)
    },
  })
})
```

#### `registerEndpoint`

`registerEndpoint` memungkinkan kamu membuat *endpoint* Nitro yang mengembalikan data *mock*. Ini sangat berguna kalau kamu ingin menguji komponen yang melakukan permintaan ke API untuk menampilkan data tertentu.

Argumen pertama adalah nama *endpoint* (misalnya `/test/`).
Argumen kedua adalah fungsi *factory* yang mengembalikan data *mock* tersebut.

Sebagai contoh, untuk melakukan *mock* pada *endpoint* `/test/`, kamu bisa melakukannya seperti ini:

```ts twoslash
import { registerEndpoint } from '@nuxt/test-utils/runtime'

registerEndpoint('/test/', () => ({
  test: 'test-field',
}))
```

Secara bawaan, permintaan kamu akan dibuat menggunakan metode `GET`. Kamu bisa menggunakan metode lain dengan menyetel objek sebagai argumen kedua, alih-alih sebuah fungsi.

```ts twoslash
import { registerEndpoint } from '@nuxt/test-utils/runtime'

registerEndpoint('/test/', {
  method: 'POST',
  handler: () => ({ test: 'test-field' }),
})
```

Objek ini menerima properti berikut:

- `handler`: fungsi penangan *event*
- `method`: (opsional) metode HTTP yang ingin dicocokkan (misalnya, 'GET', 'POST')
- `once`: (opsional) kalau diatur `true`, *handler* hanya akan digunakan untuk permintaan yang cocok pertama kali, lalu secara otomatis dihapus

> **Catatan**: Kalau permintaan di komponenmu mengarah ke API eksternal, kamu bisa memanfaatkan `baseURL` lalu mengosongkannya menggunakan [Konfigurasi Override Lingkungan Nuxt](/docs/4.x/getting-started/configuration#environment-overrides) (`$test`) agar semua permintaan kamu dialihkan ke server Nitro.

#### Konflik dengan Pengujian *End-To-End*

`@nuxt/test-utils/runtime` dan `@nuxt/test-utils/e2e` perlu berjalan di lingkungan pengujian yang berbeda, sehingga keduanya tidak bisa digunakan di dalam file yang sama.

Kalau kamu ingin menggunakan fungsionalitas pengujian *end-to-end* dan *unit* dari `@nuxt/test-utils` secara bersamaan, kamu bisa memisahkan pengujian ke dalam file yang berbeda. Kamu kemudian bisa menentukan lingkungan pengujian per-file dengan komentar khusus `// @vitest-environment nuxt`, atau menamai file pengujian *unit runtime* kamu dengan ekstensi `.nuxt.spec.ts`.

`app.nuxt.spec.ts`

```ts twoslash
import { mockNuxtImport } from '@nuxt/test-utils/runtime'

mockNuxtImport('useState', () => {
  return () => {
    return { value: 'mocked storage' }
  }
})
```

`app.e2e.spec.ts`

```ts twoslash
import { $fetch, setup } from '@nuxt/test-utils/e2e'

await setup({
  setupTimeout: 10000,
})

// ...
```

### Menggunakan `@vue/test-utils` Secara Mandiri

Kalau kamu lebih suka menggunakan `@vue/test-utils` sendiri untuk pengujian *unit* di Nuxt, dan kamu hanya menguji komponen yang tidak bergantung pada *composable* Nuxt, *auto-import*, atau *konteks* Nuxt, kamu bisa mengikuti langkah-langkah berikut untuk mengaturnya.

1. Pasang dependensi yang dibutuhkan

   ::code-group{sync="pm"}
   ```bash [npm]
   npm i --save-dev vitest @vue/test-utils happy-dom @vitejs/plugin-vue
   ```
   ```bash [yarn]
   yarn add --dev vitest @vue/test-utils happy-dom @vitejs/plugin-vue
   ```
   ```bash [pnpm]
   pnpm add -D vitest @vue/test-utils happy-dom @vitejs/plugin-vue
   ```
   ```bash [bun]
   bun add --dev vitest @vue/test-utils happy-dom @vitejs/plugin-vue
   ```
   ::

## Pengujian *End-To-End*

Untuk pengujian *end-to-end*, kami mendukung [Vitest](https://github.com/vitest-dev/vitest), [Jest](https://jestjs.io), [Cucumber](https://cucumber.io/), dan [Playwright](https://playwright.dev/) sebagai *runner* pengujian.

### Pengaturan

Di setiap blok `describe` yang memanfaatkan metode *helper* `@nuxt/test-utils/e2e`, kamu perlu menyiapkan konteks pengujian terlebih dahulu sebelum memulainya.

```ts twoslash [test/my-test.spec.ts]
import { describe, test } from 'vitest'
import { $fetch, setup } from '@nuxt/test-utils/e2e'

describe('Pengujian saya', async () => {
  await setup({
    // opsi konteks pengujian
  })

  test('pengujian saya', () => {
    // ...
  })
})
```

Di balik layar, `setup` menjalankan serangkaian tugas di dalam `beforeAll`, `beforeEach`, `afterEach`, dan `afterAll` untuk menyiapkan lingkungan pengujian Nuxt dengan benar.

Silakan gunakan opsi di bawah ini untuk metode `setup`.

#### Konfigurasi Nuxt

- `rootDir`: Jalur ke direktori tempat aplikasi Nuxt yang akan diuji berada.
  - Tipe: `string`
  - Bawaan: `'.'`
- `configFile`: Nama file konfigurasi.
  - Tipe: `string`
  - Bawaan: `'nuxt.config'`

<!--
- `config`: Objek yang berisi penimpaan konfigurasi.
  - Tipe: `NuxtConfig`
  - Bawaan: `{}` -->

#### Waktu (*Timings*)

- `setupTimeout`: Jumlah waktu (dalam milidetik) yang diberikan untuk `setupTest` agar bisa menyelesaikan tugasnya (yang bisa mencakup proses *build* atau pembuatan file untuk aplikasi Nuxt, tergantung pada opsi yang diberikan).
  - Tipe: `number`
  - Bawaan: `120000` atau `240000` pada sistem Windows

- `teardownTimeout`: Jumlah waktu (dalam milidetik) yang diberikan untuk menghancurkan lingkungan pengujian, seperti menutup *browser*.
  - Tipe: `number`
  - Bawaan: `30000`

#### Fitur

- `build`: Apakah akan menjalankan langkah *build* terpisah.
  - Tipe: `boolean`
  - Bawaan: `true` (akan menjadi `false` kalau `browser` atau `server` dinonaktifkan, atau kalau sebuah `host` disediakan)

- `server`: Apakah akan menjalankan *server* untuk merespons permintaan di dalam suite pengujian.
  - Tipe: `boolean`
  - Bawaan: `true` (akan menjadi `false` kalau sebuah `host` disediakan)

- `port`: Kalau disediakan, ini akan mengatur port *server* pengujian yang berjalan ke nilai yang ditentukan.
  - Tipe: `number | undefined`
  - Bawaan: `undefined`

- `host`: Kalau disediakan, ini akan menjadi URL yang digunakan sebagai target pengujian, alih-alih membangun dan menjalankan *server* baru. Ini sangat berguna untuk menjalankan pengujian *end-to-end* "sungguhan" terhadap versi aplikasi yang sudah di-*deploy*, atau terhadap *server* lokal yang sudah berjalan (yang bisa secara signifikan memangkas waktu eksekusi pengujian). Lihat [contoh *end-to-end target host* di bawah ini](/docs/4.x/getting-started/testing#contoh-end-to-end-target-host).
  - Tipe: `string`
  - Bawaan: `undefined`

- `browser`: Di balik layar, utilitas pengujian Nuxt menggunakan [`playwright`](https://playwright.dev) untuk menjalankan pengujian *browser*. Kalau opsi ini diatur, sebuah *browser* akan diluncurkan dan bisa dikendalikan di suite pengujian selanjutnya.
  - Tipe: `boolean`
  - Bawaan: `false`
- `browserOptions`
  - Tipe: `object` dengan properti berikut
    - `type`: Tipe *browser* yang akan diluncurkan — bisa berupa `chromium`, `firefox`, atau `webkit`
    - `launch`: `object` berisi opsi yang akan diteruskan ke *playwright* saat meluncurkan *browser*. Lihat [referensi API lengkapnya](https://playwright.dev/docs/api/class-browsertype#browser-type-launch).
- `runner`: Menentukan *runner* untuk suite pengujian. Saat ini, [Vitest](https://vitest.dev) paling kami rekomendasikan.
  - Tipe: `'vitest' | 'jest' | 'cucumber'`
  - Bawaan: `'vitest'`

- `logLevel`: Menimpa tingkat *log* consola untuk *subprocess* server. (gunakan variabel lingkungan NUXT_TEST_LOG_LEVEL untuk menimpa)
  - Tipe: `number`
  - Bawaan: `1`
- `captureServerLogs`: Apakah akan menangkap keluaran proses *server* alih-alih mewariskan *stdio*. Kalau `true` (bawaan), *stdout/stderr* server akan disembunyikan dari konsol dan dapat diakses melalui `getServerLogs()`. Atur ke `false` untuk mengembalikan perilaku *stdio inherit* yang lama (berguna saat melakukan *debug* pengujian secara lokal).
  - Tipe: `boolean`
  - Bawaan: `true`

##### Contoh *End-To-End Target Host*

Kasus penggunaan yang umum untuk pengujian *end-to-end* adalah menjalankan pengujian terhadap aplikasi yang sudah di-*deploy* dan berjalan di lingkungan yang sama seperti yang digunakan untuk Produksi.

Untuk *development* lokal atau *pipeline deploy* otomatis, pengujian terhadap *server* lokal yang terpisah bisa lebih efisien dan biasanya lebih cepat dibandingkan membiarkan *framework* pengujian membangun ulang aplikasi di antara pengujian.

Untuk memanfaatkan *target host* terpisah untuk pengujian *end-to-end*, kamu cukup memberikan properti `host` pada fungsi `setup` dengan URL yang diinginkan.

```ts
import { createPage, setup } from '@nuxt/test-utils/e2e'
import { describe, expect, it } from 'vitest'

describe('halaman login', async () => {
  await setup({
    host: 'http://localhost:8787',
  })

  it('menampilkan kolom email dan kata sandi', async () => {
    const page = await createPage('/login')
    expect(await page.getByTestId('email').isVisible()).toBe(true)
    expect(await page.getByTestId('password').isVisible()).toBe(true)
  })
})
```

### API

#### `$fetch(url)`

Mengambil HTML dari halaman yang di-*render* oleh *server*.

```ts twoslash
import { $fetch } from '@nuxt/test-utils/e2e'

const html = await $fetch('/')
```

#### `fetch(url)`

Mengambil respons dari halaman yang di-*render* oleh *server*.

```ts twoslash
import { fetch } from '@nuxt/test-utils/e2e'

const res = await fetch('/')
const { body, headers } = res
```

#### `url(path)`

Mengambil URL lengkap untuk halaman tertentu (termasuk port tempat *server* pengujian berjalan).

```ts twoslash
import { url } from '@nuxt/test-utils/e2e'

const pageUrl = url('/page')
// 'http://localhost:6840/page'
```

#### `getServerLogs()`

Mengembalikan baris-baris yang tertangkap dari *stdout/stderr* *subprocess server* sejak panggilan `startServer()` terakhir (atau `clearServerLogs()`). Hanya akan terisi kalau `captureServerLogs` bernilai `true` (yang merupakan bawaannya).

```ts twoslash
import { expect, it, vi } from 'vitest'
import { $fetch, clearServerLogs, getServerLogs } from '@nuxt/test-utils/e2e'

it('menangkap keluaran console.log dari rute server', async () => {
  clearServerLogs()
  await $fetch('/api/log-test')
  await vi.waitFor(() => {
    expect(getServerLogs().some(line => line.includes('[test] server-log-marker'))).toBe(true)
  })
})
```

#### `clearServerLogs()`

Menghapus baris *log server* yang sudah tertangkap. Ini sangat berguna di antara permintaan (*request*) kalau kamu hanya ingin memastikan atau melakukan *assert* pada *log* yang dihasilkan oleh operasi spesifik tertentu saja.

Kamu bisa menemukan informasi lebih lanjut mengenai metode *API* yang tersedia di [dokumentasi Playwright](https://playwright.dev/docs/api/class-page).
