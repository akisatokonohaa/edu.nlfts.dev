## Memperbarui Nuxt

### Rilis Terbaru

Aku akan tunjukkan caranya agar kamu bisa memperbarui Nuxt ke [versi terbaru](https://github.com/nuxt/nuxt/releases). Kamu cukup menjalankan perintah `nuxt upgrade` di terminal.

::code-group{sync="pm"}

```bash [npm]
npx nuxt upgrade
```

```bash [yarn]
yarn nuxt upgrade
```

```bash [pnpm]
pnpm nuxt upgrade
```

```bash [bun]
bun x nuxt upgrade
```

```bash [deno]
deno x nuxt upgrade
```

::

### Saluran Rilis Nightly

Kalau kamu penasaran dan ingin merasakan fitur baru sebelum resmi dirilis ke publik, kamu bisa membaca panduan mengenai *nightly release channel* yang sudah kami sediakan.

## Menguji Nuxt 5

Sekarang, saya akan jelaskan sedikit mengenai pengujian Nuxt 5. Saat ini, Nuxt 5 **masih dalam tahap pengembangan**. Meskipun begitu, mulai dari Nuxt versi 4.2 ke atas, kamu sudah bisa mencoba dan menguji berbagai perubahan besar yang akan hadir di Nuxt 5.

### Mengaktifkan Kompatibilitas Nuxt 5

Langkah pertama, pastikan kamu sudah memperbarui Nuxt ke [versi terbaru](https://github.com/nuxt/nuxt/releases).

Setelah itu, kamu bisa mengatur `future.compatibilityVersion` agar sistem berperilaku seperti Nuxt 5:

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  future: {
    compatibilityVersion: 5,
  },
})
```

Ketika kamu menetapkan nilai tersebut menjadi `5`, seluruh konfigurasi bawaan Nuxt akan berubah untuk mengadopsi perilaku versi 5, yang mencakup:

- **Vite Environment API**: Menggunakan *API* Vite terbaru untuk meningkatkan konfigurasi *build*.
- ***Routing* yang sensitif terhadap huruf**: Rute halaman akan mencocokkan huruf besar/kecil secara persis dengan URL, selaras dengan cara kerja Nitro.
- **Normalisasi Nama Halaman**: Nama komponen halaman akan disesuaikan dengan nama rutenya, agar perilaku `<KeepAlive>` tetap konsisten.
- **`clearNuxtState` kembali ke nilai awal**: Fungsi `clearNuxtState` sekarang akan mengembalikan *state* ke nilai awalnya, bukan lagi mengubahnya menjadi `undefined`.
- ***callHook* yang tidak bersifat *async***: `callHook` kini bisa mengembalikan `void` alih-alih selalu mengembalikan `Promise`.
- **Placeholder berupa node komentar**: Komponen *client-only* kini menggunakan *comment node* sebagai pengganti `<div>` untuk *placeholder* SSR, yang mana ini memperbaiki masalah *hydration* pada *scoped styles*.
- **Import *side-effect* yang lebih ketat**: File `tsconfig.json` yang dihasilkan akan mengaktifkan `noUncheckedSideEffectImports` untuk mengikuti standar bawaan TypeScript 7.
- **Vue Options API dinonaktifkan**: *Options API* tidak lagi dikompilasi ke dalam *bundle* klien demi mengurangi ukuran berkas.
- **Augmentasi tipe `process.*` dihapus**: TypeScript tidak lagi menampilkan *flag* `process.*` yang sudah usang pada `NodeJS.Process`.
- **Halaman bertipe (*Typed Pages*)**: Fitur `experimental.typedPages` diaktifkan secara bawaan agar pengecekan tipe pada *routing* berjalan dengan baik.
- **`baseUrl` pada TypeScript diabaikan**: Konfigurasi TypeScript yang dihasilkan tidak lagi memakai `compilerOptions.baseUrl` untuk menyelesaikan *alias* Nuxt.
- Serta berbagai peningkatan dan perubahan Nuxt 5 lainnya yang akan terus hadir.

::note
Bagian ini bisa berubah sewaktu-waktu sampai versi final resmi dirilis. Jadi, pastikan kamu sering mengecek halaman ini kalau sedang menguji Nuxt 5 menggunakan pengaturan `future.compatibilityVersion: 5`.
::

Perubahan yang bersifat *breaking* atau penting akan aku catat di bawah ini beserta langkah-langkah migrasinya agar tetap kompatibel.

### Augmentasi Tipe `process.*` Dihapus

🚦 **Tingkat Dampak**: Minimal

#### Apa yang Berubah

Dulu, Nuxt menambahkan properti seperti `browser`, `client`, `dev`, `server`, dan `test` ke dalam `NodeJS.Process`. Sekarang tidak lagi. *Define* saat *build* untuk *flag* tersebut masih tetap ada demi kompatibilitas, tapi TypeScript tidak akan lagi memperlakukannya sebagai properti yang dikenali.

Saya sarankan kamu untuk beralih menggunakan [`import.meta.*`](/docs/4.x/api/advanced/import-meta). *Flag* tersebut akan diganti saat proses *build* dan tetap bisa di-*tree-shake* dengan baik.

#### Langkah Migrasi

Ganti pengecekan lama di kode aplikasi, *module*, maupun *library* kamu:

```ts
// Sebelumnya
// eslint-disable-next-line nuxt/prefer-import-meta
if (process.server) {
  /* ... */
}

// Sekarang
if (import.meta.server) {
  /* ... */
}
```

Aturan ESLint [`nuxt/prefer-import-meta`](https://eslint.nuxt.com/packages/plugin#nuxtprefer-import-meta) akan memberi tanda kalau ada penggunaan `process.*` yang masih tersisa di kode kamu.

### *Routing* Sensitif Terhadap Huruf (Case-Sensitive)

🚦 **Tingkat Dampak**: Minimal

#### Apa yang Berubah

Dengan mengaktifkan `compatibilityVersion: 5`, rute halaman akan membedakan huruf besar dan kecil (bersifat *case-sensitive*), sebagaimana cara kerja Nitro. Sebagai contoh, URL `/About` tidak lagi akan mencocokkan dengan file `pages/about.vue`.

#### Langkah Migrasi

Perbarui tautan (*link*) kamu agar menggunakan huruf yang sama persis dengan rute halamannya. Tapi, kalau kamu ingin mempertahankan pencocokan yang mengabaikan huruf besar/kecil, kamu bisa atur seperti ini:

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  router: {
    options: {
      sensitive: false,
    },
  },
})
```

### `jiti` Tidak Lagi Dibundel

🚦 **Tingkat Dampak**: Menengah

#### Apa yang Berubah

Nuxt tidak lagi bergantung pada [`jiti`](https://github.com/unjs/jiti). File-file yang dimuat di luar *bundler* (seperti `nuxt.config.ts`, file di dalam folder `modules/`, dan konfigurasi *layer*) kini diimpor langsung oleh *runtime* itu sendiri.

**Tenang, kamu tetap bisa menulis konfigurasi menggunakan TypeScript.** Nuxt 5 mengharuskan penggunaan Node.js versi 22.19 atau yang lebih baru, dimana fitur *type stripping* sudah aktif secara bawaan. Jadi, file `nuxt.config.ts` dan *module* TypeScript bisa dimuat secara native. Ada dua hal yang tidak bisa dilakukan oleh *runtime* (yang dulu biasa ditutup-tutupi oleh `jiti`), yaitu menebak ekstensi file secara otomatis dan mengkompilasi sintaks TypeScript yang menghasilkan kode (*emit code*).

Kalau tidak ditangani, masalah ini baru akan terlihat saat Nuxt memuat file. Oleh karena itu, file `node` tsconfig yang dihasilkan sekarang mendeskripsikan lingkungan persis seperti yang dilihat oleh *runtime* (`module` dan `moduleResolution` diatur ke `nodenext`, ditambah dengan [`erasableSyntaxOnly`](https://www.typescriptlang.org/tsconfig/#erasableSyntaxOnly)). Dengan begitu, TypeScript bisa langsung melaporkan masalahnya dari awal.

Pengaturan di atas hanya berlaku untuk `nuxt.config`, folder `modules/`, dan konfigurasi *layer*. Kode aplikasi dan folder `shared/` kamu tetap diproses melalui Vite dan diselesaikan seperti biasanya. Kalau kamu tetap butuh perilaku lama, kamu bisa menimpa pengaturannya:

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  typescript: {
    nodeTsConfig: {
      compilerOptions: {
        module: 'preserve',
        moduleResolution: 'bundler',
        erasableSyntaxOnly: false,
      },
    },
  },
})
```

#### Alasan Perubahan Ini

Dahulu, `jiti` selalu terpasang di setiap instalasi Nuxt hanya untuk memuat segelintir file, padahal sekarang *runtime* sudah bisa melakukannya sendiri. Menghapusnya membuat ukuran instalasi bawaan menjadi jauh lebih ringan.

#### Langkah Migrasi

**1. Tambahkan ekstensi file pada *relative import*.**

*Import* relatif di dalam `nuxt.config.ts`, folder `modules/`, dan konfigurasi *layer* sekarang wajib menyertakan ekstensinya secara eksplisit:

```diff [nuxt.config.ts]
- import { myPlugin } from './build/my-plugin'
+ import { myPlugin } from './build/my-plugin.ts'
```

TypeScript akan menandai ekstensi yang hilang ini sebagai error `TS2835`. Sebagai catatan, *quick fix* dari TypeScript biasanya menyarankan `./build/my-plugin.js`; abaikan itu dan tulis ekstensi asli file-nya (`.ts`), karena Node bisa menyelesaikannya secara langsung.

Untuk *import* paket biasa (seperti `import { defu } from 'defu'`), aturan ini tidak berlaku dan tetap aman.

**2. Gunakan sintaks TypeScript yang bisa dihapus (*erasable*).**

Anotasi tipe akan dihapus, tapi sintaks yang menghasilkan kode *runtime* tidak bisa. Di dalam file konfigurasi dan *module*, gantilah:

- `enum Foo {}` menjadi objek `const`.
- Blok `namespace` / `module` menjadi *export* biasa.
- *Constructor parameter properties* (seperti `constructor(private x: string) {}`) menjadi assignment yang ditulis manual.
- *Decorator* eksperimental.

TypeScript akan otomatis melaporkan semua hal di atas sebagai error `TS1294`.

**3. Kalau kamu mempublikasikan *layer* atau *module*, kirimkan dalam bentuk JavaScript yang sudah dikompilasi.**

Poin ini khusus untuk paket/ *package*. *Runtime* akan menolak untuk menghapus tipe dari file apa pun yang berada di dalam `node_modules`, terlepas dari konfigurasinya. Jadi, *entrypoint* yang ditulis dalam TypeScript dan dipublikasikan tidak bisa dimuat secara native, sekalipun versi Node-mu sudah sangat baru. Kamu harus mengkompilasinya ke JavaScript sebelum dipublikasikan. Jika paketmu menyertakan file `nuxt.config`, pastikan untuk mengekspornya sebagai `nuxt.config.mjs`. Kalau tidak, setiap proyek yang menggunakan paketmu akan terpaksa memasang `jiti`.

Aturan ini tidak berlaku untuk *layer* di dalam proyekmu sendiri: file `layers/*/nuxt.config.ts` tetap bisa dimuat secara *native*.

**4. Pasang `jiti` kalau kamu masih tetap membutuhkannya.**

Sekarang, `jiti` berstatus sebagai *peer dependency* opsional. Kamu bisa memasangnya, dan Nuxt akan langsung menggunakannya sebagai *fallback* otomatis ketika *runtime* tidak bisa memuat sebuah file sendiri:

::code-group{sync="pm"}

```bash [npm]
npm i -D jiti
```

```bash [yarn]
yarn add -D jiti
```

```bash [pnpm]
pnpm add -D jiti
```

```bash [bun]
bun add -D jiti
```

::

Satu pengecualian yang perlu kamu tahu: file `nuxt.schema` akan selalu membutuhkan `jiti`, tanpa peduli versi Node.js yang kamu gunakan. Alasannya, anotasi JSDoc di dalamnya dibaca melalui proses *transform* saat impor, bukan dengan cara mengimpor file tersebut secara langsung.

Ada satu perubahan kecil lainnya yang menyertai hal ini: *plugin* PostCSS yang kamu tulis di `postcss.plugins` kini diselesaikan oleh *runtime*. Jadi, nama *plugin* yang sebelumnya hanya bisa dikenali karena adanya entri `alias` di Nuxt, sekarang tidak akan bisa dimuat. Kamu harus menggunakan nama paket yang sebenarnya atau menuliskan jalur (*path*) filenya secara lengkap.

### Migrasi ke Vite Environment API

🚦 **Tingkat Dampak**: Menengah

#### Apa yang Berubah

Nuxt 5 bermigrasi menggunakan *API* [Environment API terbaru dari Vite 6](https://vite.dev/guide/api-environment). Perubahan ini meng formalisasi konsep lingkungan (*environment*) dan memberikan kendali yang jauh lebih baik terhadap konfigurasi di setiap lingkungan.

Dahulu, Nuxt menggunakan konfigurasi Vite yang terpisah antara klien dan server. Sekarang, Nuxt menggunakan satu konfigurasi Vite yang digunakan bersama, lengkap dengan *plugin* spesifik lingkungan yang memanfaatkan metode `applyToEnvironment()` untuk menargetkan lingkungan tertentu.

::note
*Vite Environment API* selalu aktif di Nuxt 5. Opsi `experimental.viteEnvironmentApi` sudah kami hapus.
::

**Perubahan utama yang terjadi:**

1. **`extendViteConfig()` spesifik lingkungan sudah tidak direkomendasikan**: Opsi `server` dan `client` di dalam `extendViteConfig()` sekarang usang dan akan menampilkan peringatan kalau kamu tetap menggunakannya.

2. **Cara pendaftaran *plugin* berubah**: *Plugin* Vite yang didaftarkan melalui `addVitePlugin()` dan hanya menargetkan satu lingkungan (dengan memberikan `server: false` atau `client: false`) tidak akan lagi memanggil *hook* `config` atau `configResolved`-nya.

3. **Konfigurasi bersama (*shared*)**: *Hook* `vite:extendConfig` dan `vite:configResolved` sekarang bekerja pada konfigurasi yang digunakan bersama, bukan konfigurasi klien/server yang terpisah.

#### Alasan Perubahan Ini

*Vite Environment API* memberikan berbagai keuntungan seperti:
- Konsistensi yang lebih baik antara proses *development* dan *build production*
- Kendali yang lebih detail atas konfigurasi berdasarkan lingkungannya
- Peningkatan performa dan arsitektur *plugin* yang lebih rapi
- Dukungan untuk lingkungan (*environment*) kustom di luar sekadar klien dan server

#### Langkah Migrasi

##### 1. Beralihlah menggunakan *Plugin* Vite

Kami sangat menyarankan kamu untuk mulai menggunakan *plugin* Vite sebagai pengganti `extendViteConfig`, `vite:configResolved`, maupun `vite:extendConfig`.

```ts
// Sebelumnya
extendViteConfig((config) => {
  config.optimizeDeps.include.push('my-package')
}, { server: false })

nuxt.hook('vite:extendConfig' /* or vite:configResolved */, (config, { isClient }) => {
  if (isClient) {
    config.optimizeDeps.include.push('my-package')
  }
})

// Sekarang
addVitePlugin(() => ({
  name: 'my-plugin',
  config (config) {
    // kamu bisa mengatur konfigurasi vite global di sini
  },
  configResolved (config) {
    // kamu bisa mengakses konfigurasi vite yang sudah diselesaikan sepenuhnya di sini
  },
  configEnvironment (name, config) {
    // kamu bisa mengatur konfigurasi vite berdasarkan lingkungan di sini
    if (name === 'client') {
      config.optimizeDeps ||= {}
      config.optimizeDeps.include ||= []
      config.optimizeDeps.include.push('my-package')
    }
  },
  applyToEnvironment (environment) {
    return environment.name === 'client'
  },
}))
```

##### 2. Migrasikan *Plugin* Vite untuk Menggunakan Lingkungan

Alih-alih menggunakan `addVitePlugin` dengan parameter `server: false` atau `client: false`, sekarang kamu sebaiknya memanfaatkan *hook* `applyToEnvironment` yang baru di dalam *plugin* kamu.

```ts
// Sebelumnya
addVitePlugin(() => ({
  name: 'my-plugin',
  config (config) {
    config.optimizeDeps.include.push('my-package')
  },
}), { client: false })

// Sekarang
addVitePlugin(() => ({
  name: 'my-plugin',
  config (config) {
    // kamu bisa mengatur konfigurasi vite global di sini
  },
  configResolved (config) {
    // kamu bisa mengakses konfigurasi vite yang sudah diselesaikan sepenuhnya di sini
  },
  configEnvironment (name, config) {
    // kamu bisa mengatur konfigurasi vite berdasarkan lingkungan di sini
    if (name === 'client') {
      config.optimizeDeps ||= {}
      config.optimizeDeps.include ||= []
      config.optimizeDeps.include.push('my-package')
    }
  },
  applyToEnvironment (environment) {
    return environment.name === 'client'
  },
}))
```

::read-more{to="https://vite.dev/guide/api-environment" target="_blank"}
Pelajari lebih lanjut mengenai *Environment API* milik Vite
::

### Migrasi ke Vite 8

🚦 **Tingkat Dampak**: Menengah

#### Apa yang Berubah

Nuxt 5 meningkatkan versinya dari Vite 7 ke [Vite 8](https://main.vite.dev/guide/migration). Di versi ini, *esbuild* dan *Rollup* digantikan oleh [Rolldown](https://rolldown.rs) sebagai *bundler* dasarnya. Ini membuat proses *build* menjadi jauh lebih cepat, tetapi juga membawa beberapa perubahan besar.

::note
Berbeda dengan migrasi *Vite Environment API*, perubahan ini tidak bisa kamu aktifkan lebih awal hanya dengan mengatur `future.compatibilityVersion: 5`. Kalau kamu ingin menguji kompatibilitas Vite 8 sebelum waktunya, kamu bisa menambahkan *override* resolusi `"vite": "^8.0.0-beta.15"` di file `package.json` milikmu.
::

Sebagian besar proses migrasi sudah kami tangani secara internal di dalam Nuxt, tapi ada beberapa perubahan yang akan langsung kamu temui:

- **`vite.esbuild` dan `vite.optimizeDeps.esbuildOptions`** sudah tidak lagi direkomendasikan. Gantikan dengan `vite.oxc` dan `vite.optimizeDeps.rolldownOptions`. Saat ini Vite 8 masih secara otomatis mengonversinya, tapi opsi lama tersebut akan dihapus di masa mendatang.
- **`build.rollupOptions`** sudah tidak lagi direkomendasikan. Gantikan dengan `build.rolldownOptions`.
- **Perilaku *CommonJS interop*** telah berubah. Kalau kamu mengimpor *module* CJS, saya sarankan kamu untuk meninjau [panduan migrasi Vite 8](https://main.vite.dev/guide/migration#consistent-commonjs-interop) untuk detail lengkapnya.

::read-more{to="https://main.vite.dev/guide/migration" target="_blank"}
Lihat panduan migrasi Vite 8 secara lengkap untuk semua perubahan dan langkah migrasinya.
::

### Migrasi ke Nitro v3

🚦 **Tingkat Dampak**: Signifikan

#### Apa yang Berubah

Nuxt 5 melakukan peningkatan besar ke [Nitro v3](https://nitro.build/blog/v3-beta), yang merupakan penulisan ulang total dari *engine* server. Nitro v3 dibangun di atas [srvx](https://srvx.h3.dev) dan [h3 v2](https://h3.dev), mengadopsi *API* standar Web `Request`/`Response` di seluruh bagiannya. Ini membawa peningkatan performa dan *API* yang lebih konsisten, sayangnya juga disertai beberapa perubahan besar pada kode sisi server.

::important
Kami masih terus bekerja untuk mengintegrasikan Nitro v3, jadi kamu bisa berharap akan ada perubahan tambahan serta upaya lebih lanjut agar proses migrasi ini menjadi lebih mudah.
::

::read-more{to="https://nitro.build/blog/v3-beta" target="_blank"}
Baca pengumuman *beta* Nitro v3 untuk gambaran keseluruhannya.
::

::read-more{to="https://nitro.build/docs/migration" target="_blank"}
Lihat panduan migrasi Nitro v3 yang lengkap untuk semua perubahan besarnya.
::

Bagian di bawah ini akan menyoroti perubahan yang paling relevan bagi kamu, baik sebagai pengembang aplikasi Nuxt maupun penulis *module*.

#### Perubahan Paket dan Jalur Impor (*Import Path*)

Paket `nitropack` sudah berganti nama menjadi `nitro`. Semua jalur impor telah berubah:

| Sebelumnya | Sekarang |
|---|---|
| `nitropack` | `nitro` |
| `nitropack/types` | `nitro/types` |
| `nitropack/runtime` | `nitro` |
| `h3` (untuk utilitas server) | `nitro/h3` |

*Auto-import* di dalam rute server (`defineEventHandler`, `getQuery`, `readBody`, `useRuntimeConfig`, dan lain-lain) tetap berjalan normal tanpa perlu diubah.

Tapi, kalau kamu memiliki impor eksplisit di kode server, silakan perbarui:

```diff
- import { defineEventHandler, getQuery } from 'h3'
+ import { defineEventHandler, getQuery } from 'nitro/h3'
```

**Khusus untuk kamu para penulis *module***, augmentasi tipe sekarang harus menargetkan jalur *module* yang baru:

```diff
- declare module 'nitropack/types' {
+ declare module 'nitro/types' {
    interface NitroRouteRules {
      myModule?: { /* ... */ }
    }
  }
```

#### Penanganan Error: `status`/`statusText` Menggantikan `statusCode`/`statusMessage`

h3 v2 mengubah nama properti *error* agar selaras dengan standar Web:

```diff
  createError({
-   statusCode: 404,
-   statusMessage: 'Not Found',
+   status: 404,
+   statusText: 'Not Found',
  })
```

Di dalam rute server, kelas *error* sekarang adalah `HTTPError` (menggantikan `createError` dari `h3`):

```diff
- import { createError } from 'h3'
+ import { HTTPError } from 'nitro/h3'

  export default defineEventHandler(() => {
-   throw createError({ statusCode: 400, statusMessage: 'Bad request' })
+   throw new HTTPError({ status: 400, statusText: 'Bad request' })
  })
```

::note
Di bagian Vue pada aplikasimu (folder `app/`), *composable* `createError` milik Nuxt tetap bisa digunakan dan itu adalah cara yang paling kami rekomendasikan untuk melempar *error*.
::

#### `createError` Tidak Lagi Mengembalikan Instansi `HTTPError`

`NuxtError` sekarang menjadi kelasnya sendiri, bukan lagi sub-kelas dari `HTTPError` milik h3. Jadi, pengecekan `instanceof HTTPError` tidak akan lagi cocok untuk *error* yang dibuat menggunakan `createError` milik Nuxt. Selain itu, semuanya tetap sama: *error* tetap memiliki properti yang sama, diserialisasi dengan cara yang sama, dan tetap dipetakan ke respons HTTP yang tepat saat SSR.

Kalau kamu biasanya mempersempit jenis *error* berdasarkan kelasnya, gunakan salah satu *predicates* berikut:

```diff
- if (error instanceof HTTPError) {
+ if (HTTPError.isError(error)) {
    // akan menangani baik `new HTTPError()` maupun `createError()` milik Nuxt
  }
```

```diff
+ import { isNuxtError } from '#app'
+
+ if (isNuxtError(error)) {
+   // akan mempersempit ke error yang dibuat menggunakan `createError` milik Nuxt
+ }
```

#### Perubahan *API* Event Server (h3 v2)

Objek `H3Event` sekarang menggunakan *API* standar Web:

**Properti *Request*:**
```diff
- event.path              // string
+ event.url.pathname      // objek URL - gunakan .pathname, .search, .hash

- event.method            // string
+ event.req.method        // melalui objek Web Request

- event.node.req.headers  // Node.js IncomingHttpHeaders
+ event.req.headers       // Web Headers API (.get(), .set(), .has())
```

**Properti *Response*:**
```diff
- event.node.res.statusCode = 200
+ event.res.status = 200

- event.node.res.statusMessage = 'OK'
+ event.res.statusText = 'OK'

- setResponseHeader(event, 'x-custom', 'value')
+ event.res.headers.set('x-custom', 'value')

- appendResponseHeader(event, 'set-cookie', cookie)
+ event.res.headers.append('set-cookie', cookie)
```

#### `useRuntimeConfig()` Tidak Lagi Menerima `event`

Di Nitro v3, `useRuntimeConfig()` tidak lagi membutuhkan (atau menerima) argumen `event` di dalam rute server:

```diff
  export default defineEventHandler((event) => {
-   const config = useRuntimeConfig(event)
+   const config = useRuntimeConfig()
  })
```

#### Aturan Rute: `statusCode` Berubah Menjadi `status`

Kalau kamu mendefinisikan aturan rute untuk pengalihan (*redirect*), nama propertinya sudah berubah:

```diff
  export default defineNuxtConfig({
    routeRules: {
      '/old-page': {
-       redirect: { to: '/new-page', statusCode: 302 },
+       redirect: { to: '/new-page', status: 302 },
      },
    },
  })
```

#### Khusus untuk Penulis *Module*: Perubahan Tambahan

- **Impor *plugin* Nitro**: Gunakan `import { definePlugin } from 'nitro'` untuk impor eksplisit (untuk *auto-import* tetap berjalan seperti biasa).
- ***Runtime hooks***: `nitroApp.hooks.hook('beforeResponse', ...)` dan `nitroApp.hooks.hook('afterResponse', ...)` sudah digabungkan dan digantikan oleh `nitroApp.hooks.hook('response', ...)`.
- **`getRouteRules()` dari `nitro/app`**: Di sisi server, *helper* Nitro berubah dari `getRouteRules(event)` menjadi `getRouteRules(method, pathname)`, yang nantinya mengembalikan objek `{ routeRules }`.

### Penghapusan `experimental.externalVue`

🚦 **Tingkat Dampak**: Minimal

#### Apa yang Berubah

Opsi `experimental.externalVue` sudah kami hapus sepenuhnya. Sekarang, dependensi *compiler* Vue (seperti `@babel/parser`, `@vue/compiler-core`, `@vue/compiler-dom`, `@vue/compiler-ssr`, dan `estree-walker`) akan selalu digantikan dengan *mock proxy* di dalam *server bundle*, asalkan `vue.runtimeCompiler` tidak diaktifkan.

#### Alasan Perubahan Ini

Seiring dengan migrasi ke Nitro v3, semua dependensi sekarang secara otomatis dibundel ke dalam output server (berbeda dengan Nitro v2 yang mengecualikan `node_modules`). Dulu, opsi `externalVue` dirancang agar Vue tetap menjadi dependensi eksternal untuk menghindari duplikasi *copy* Vue di dalam *bundle*. Namun, karena Nitro v3 tetap membundel semuanya, opsi ini menjadi tidak berguna lagi (*no-op*).

*Build* server Vue sebenarnya menyertakan rantai *compiler* yang lengkap, yang mana ini menarik paket besar seperti `@babel/parser` (465KB) ke dalam *server bundle* secara sia-sia. Paket-paket *compiler* ini hanya diperlukan kalau kamu mengaktifkan `vue.runtimeCompiler` untuk kompilasi *template* saat *runtime*.

Dengan cara selalu membuat *mock* terhadap dependensi *compiler* tersebut, ukuran *server bundle* bawaan bisa dihemat sekitar 860KB (setara ~59%).

#### Langkah Migrasi

Kalau dulu kamu pernah mengatur `experimental.externalVue` secara eksplisit, sekarang hapus saja pengaturannya tersebut.

```diff
  export default defineNuxtConfig({
    experimental: {
-     externalVue: false,
    },
  })
```

::note
Kalau kamu mengaktifkan `vue.runtimeCompiler: true`, paket *compiler* asli tetap akan disertakan seperti biasa.
::

### `experimental.parseErrorData` Tidak Lagi Dapat Dikonfigurasi

🚦 **Tingkat Dampak**: Minimal

#### Apa yang Berubah

Opsi `experimental.parseErrorData` sudah usang, dan di Nuxt 5 keadaannya dipaksa menjadi aktif (hidup). Mengaturnya ke `false` hanya akan memunculkan peringatan dan diabaikan, jadi `error.data` di halaman *error* akan selalu menjadi nilai yang persis kamu kirimkan ke `createError`.

Pada `compatibilityVersion: 4`, opsi ini masih bekerja normal dan `false` akan memberikan *string* `error.data`. Jadi, perilaku ini hanya berubah ketika kamu mengaktifkan kompatibilitas Nuxt 5.

#### Alasan Perubahan Ini

Ketika Nuxt merender halaman *error*, ia mengambil `/__nuxt_error` secara internal dan membawa *error* tersebut di dalam permintaan. Dahulu, *error* ini disebar ke beberapa parameter *query* untuk setiap bidangnya. Karena nilai *query* selalu berupa *string*, `error.data` yang sampai akan berbentuk *string* dan harus di-*parse* kembali. Opsi `parseErrorData` dulunya ada untuk memilih keluar dari proses *parsing* tersebut.

Sekarang, *error* dikirim sebagai satu parameter JSON yang sudah terenkode. Dengan begitu, `error.data` mempertahankan bentuk aslinya dan tidak pernah diubah menjadi *string*. Tipe datanya juga ikut terjaga, misalnya `status` akan tetap berupa angka, dan boolean akan tetap boolean, bukan *string* `'true'` atau `'false'`. Karena tidak ada lagi yang mengubah `error.data` menjadi *string*, opsi ini hanya tersisa untuk mengubahnya kembali menjadi *string* bagi aplikasi yang masih mengharapkan bentuk *string*.

#### Langkah Migrasi

Hapus opsi tersebut dari konfigurasi:

```diff
  export default defineNuxtConfig({
    experimental: {
-     parseErrorData: false,
    },
  })
```

Kalau dulu kamu mengaturnya ke `false` karena ingin mem-*parse* `error.data` secara manual, sekarang hapus kode *parsing* itu juga, karena `error.data` sudah mempertahankan nilai apa pun yang kamu kirimkan ke `createError`:

```diff
  <script setup lang="ts">
  import type { NuxtError } from '#app'

  const props = defineProps({
    error: Object as () => NuxtError
  })

- const data = JSON.parse(props.error.data)
+ const data = props.error.data
  </script>
```

### `giget` Sekarang Bersifat Opsional (*Remote Layers*)

🚦 **Tingkat Dampak**: Minimal

#### Apa yang Berubah

`giget` tidak lagi dipasang secara bawaan. Sekarang ia menjadi *peer dependency* opsional dari `@nuxt/kit` yang hanya dibutuhkan kalau kamu mengunduh *layer* yang nama `extends`-nya berupa URL jarak jauh:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  extends: ['github:my-org/my-theme'],
})
```

*Layer* lokal, *layer* di dalam folder `~~/layers/`, dan *layer* yang dipasang sebagai paket tidak terpengaruh oleh perubahan ini.

#### Alasan Perubahan Ini

Sebagian besar proyek tidak pernah memperluas (*extend*) dari sumber jarak jauh, jadi downloader ini hanya membebani semua orang demi melayani segelintir pengguna saja. Mengunduh *layer* pada saat resolusi konfigurasi juga merupakan cara yang paling tidak dapat direproduksi (*least reproducible*) untuk mengonsumsi *layer*: proses *fetch* terjadi di luar *package manager* kamu, jadi tidak masuk ke dalam *lockfile*, dan kecuali kamu *pin* sendiri, revisinya tidak akan terkunci.

#### Langkah Migrasi

**Cara yang paling kami rekomendasikan: pindahkan *layer* ke `package.json`.** Setiap *package manager* utama memahami URL Git, jadi *layer* jarak jauh bisa menjadi dependensi biasa. Cara ini memasukkannya ke dalam *lockfile*, menguncinya ke *commit* yang tepat, dan memasangnya berdampingan dengan dependensi lainnya:

```json [package.json]
{
  "devDependencies": {
    "my-theme": "github:my-org/my-theme#4a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b"
  }
}
```

Lalu, perpanjang (*extend*) dari nama paketnya:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  extends: ['my-theme'],
})
```

Bagian setelah tanda `#` bisa berupa *commit-ish* apa pun, jadi tag (seperti `#v1.2.0`) atau `#semver:^1.2.0` juga bisa digunakan; namun *SHA commit* yang lengkap adalah satu-satunya bentuk yang benar-benar tidak dapat diubah (*immutable*).

**Cara lainnya, pasang `giget`** dan tetap gunakan entri `extends` jarak jauh seperti sebelumnya:

::code-group{sync="pm"}

```bash [npm]
npm install -D giget
```

```bash [yarn]
yarn add -D giget
```

```bash [pnpm]
pnpm add -D giget
```

```bash [bun]
bun add -D giget
```

::

Kalau sebuah *layer* jarak jauh diselesaikan tanpa kehadiran `giget`, Nuxt akan melaporkan entri `extends` mana yang membutuhkannya.

### Penghapusan Dukungan `_renderResponse` Legasi

🚦 **Tingkat Dampak**: Minimal

#### Apa yang Berubah

`ssrContext._renderResponse` tidak lagi diperiksa sebagai cadangan (*fallback*). Sekarang, hanya `ssrContext['~renderResponse']` internal (yang diatur oleh *composable* router Nuxt) yang digunakan.

#### Alasan Perubahan Ini

Properti `_renderResponse` pada `ssrContext` awalnya dipertahankan sebagai *fallback* kompatibilitas ke belakang setelah [PR #33896](https://github.com/nuxt/nuxt/pull/33896) memigrasikan *API* internal ke `~renderResponse`. Komentar *TODO* di dalam kode sudah menandakan bahwa ini harus dihapus di Nuxt v5.

#### Langkah Migrasi

Kalau kamu secara langsung mengatur `ssrContext._renderResponse` (yang sebenarnya bukanlah *API* publik), gantilah dengan `ssrContext['~renderResponse']`. *Composable* router Nuxt sendiri sudah menggunakan properti yang baru, jadi kamu tidak perlu mengubah apa pun kalau kamu menggunakan `navigateTo` atau *route middleware*.

### `callHook` yang Tidak Bersifat *Async*

🚦 **Tingkat Dampak**: Minimal

#### Apa yang Berubah

Seiring dengan peningkatan ke [hookable v6](https://github.com/unjs/hookable), `callHook` sekarang bisa mengembalikan `void` alih-alih selalu mengembalikan `Promise<void>`. Ini adalah peningkatan performa yang signifikan karena menghindari alokasi `Promise` yang tidak perlu ketika tidak ada *hook* yang terdaftar atau ketika semua *hook* bersifat sinkron.

Secara bawaan (dengan `compatibilityVersion: 4`), Nuxt membungkus `callHook` dengan `Promise.resolve()` agar rantai `.then()` dan `.catch()` yang sudah ada tetap berjalan. Dengan `compatibilityVersion: 5`, bungkusan ini dihapus.

::tip
Perubahan ini mempengaruhi baik *hook* Nuxt saat *build-time* (yang digunakan oleh *module* Nuxt) maupun *hook* Nuxt saat *runtime* (yang mungkin kamu gunakan di kode aplikasimu).
::

#### Alasan Perubahan Ini

`callHook` di hookable v6 menjadi 20-40 kali lebih cepat karena menghindari pembuatan `Promise` saat memang tidak diperlukan. Ini sangat menguntungkan aplikasi yang memiliki banyak titik pemanggilan *hook*.

#### Langkah Migrasi

Kalau kamu atau *module* kamu menggunakan `callHook` dengan rantai `.then()` atau `.catch()`, ubahlah menjadi `await`:

```diff
- nuxtApp.callHook('my:hook', data).then(() => { ... })
+ await nuxtApp.callHook('my:hook', data)
```

```diff
- nuxtApp.hooks.callHook('my:hook', data).catch(err => { ... })
+ try { await nuxtApp.hooks.callHook('my:hook', data) } catch (err) { ... }
```

::tip
Kamu bisa menguji fitur ini lebih awal dengan mengatur `future.compatibilityVersion: 5` (lihat bagian [Pengujian Nuxt 5](/docs/4.x/getting-started/upgrade#testing-nuxt-5)) atau dengan mengaktifkannya secara eksplisit melalui `experimental.asyncCallHook: false`.
::

Sebagai alternatif lain, kamu bisa memastikan `callHook` selalu mengembalikan `Promise` dengan pengaturan berikut:

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    asyncCallHook: true,
  },
})
```

### *Placeholder* Komentar untuk *Client-Only*

🚦 **Tingkat Dampak**: Minimal

#### Apa yang Berubah

Dengan `compatibilityVersion: 5`, komponen *client-only* (file `.client.vue` dan *wrapper* `createClientOnly()`) sekarang akan merender *comment* HTML (`<!--placeholder-->`) di sisi server, sebagai pengganti elemen `<div>` kosong.

#### Alasan Perubahan Ini

Ketika *placeholder* `<div>` dan elemen akar komponen asli memiliki nama tag yang sama, *runtime* Vue akan melewatkan penerapan ulang `setScopeId` selama proses *hydration*. Ini menyebabkan *scoped styles* menghilang setelah komponen dimuat. Dengan menggunakan *comment node*, tabrakan nama tag bisa dihindari sepenuhnya.

#### Langkah Migrasi

Kalau kamu mengandalkan *placeholder* `<div>` untuk mewarisi atribut (`class`, `style`, dll.) demi keperluan tata letak (misalnya, menyediakan ruang agar tidak terjadi pergeseran tata letak), bungkuslah komponen tersebut di dalam `<ClientOnly>` beserta *slot* `#fallback`:

```diff
- <MyComponent class="placeholder" style="min-height: 200px" />
+ <ClientOnly>
+   <MyComponent />
+   <template #fallback>
+     <div class="placeholder" style="min-height: 200px"></div>
+   </template>
+ </ClientOnly>
```

::tip
Kamu bisa menguji fitur ini lebih awal dengan mengatur `future.compatibilityVersion: 5` (lihat bagian [Pengujian Nuxt 5](/docs/4.x/getting-started/upgrade#testing-nuxt-5)) atau dengan mengaktifkannya secara eksplisit melalui `experimental.clientNodePlaceholder: true`.
::

Sebagai alternatif lain, kamu bisa mengembalikan perilaku *placeholder* `<div>` yang lama dengan:

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    clientNodePlaceholder: false,
  },
})
```

### *Side-Effect Import* yang Lebih Ketat

🚦 **Tingkat Dampak**: Minimal

#### Apa yang Berubah

Dengan `compatibilityVersion: 5`, file `tsconfig.json` yang dihasilkan oleh Nuxt akan mengaktifkan [`noUncheckedSideEffectImports`](https://www.typescriptlang.org/tsconfig/#noUncheckedSideEffectImports). Ini merupakan bawaan di TypeScript 7, jadi mengadopsinya sejak sekarang akan membuat proyekmu selalu selaras ketika kamu meningkatkan versi nanti.

Dengan opsi ini aktif, *import* yang hanya mengandung *side-effect* (seperti `import './setup'`) yang tidak bisa diselesaikan oleh TypeScript ke sebuah *module* sekarang akan dianggap sebagai *error* tipe, padahal dulu biasanya diabaikan. Perlu diingat, ini hanya mempengaruhi pengecekan tipe (`nuxt typecheck` dan editor kamu), tidak pada perilaku *runtime*.

#### Alasan Perubahan Ini

*Side-effect import* yang tidak bisa diselesaikan sebelumnya diam-diam diabaikan, sehingga kesalahan ketik atau file yang terhapus bisa lolos dari pengecekan tipe. Dengan menandainya, kesalahan-kesalahan ini akan tertangkap dan sesuai dengan standar bawaan TypeScript 7.

#### Langkah Migrasi

Kalau pengecekan tipe tiba-tiba menampilkan *error* pada *side-effect import* dari aset non-kode (contohnya `import '~/assets/styles.css'`), tambahkan deklarasi *ambient module* agar TypeScript tahu bahwa *import* tersebut valid:

```ts [types.d.ts]
declare module '*.css' {}
```

::tip
Kamu bisa kembali ke perilaku sebelumnya dengan menonaktifkan opsi ini di `nuxt.config` milikmu:

<!-- @case-police-ignore tsConfig -->

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  typescript: {
    tsConfig: {
      compilerOptions: {
        noUncheckedSideEffectImports: false,
      },
    },
  },
})
```
::

### Vue Options API Dinonaktifkan Secara Bawaan

🚦 **Tingkat Dampak**: Minimal

#### Apa yang Berubah

Dengan `compatibilityVersion: 5`, Nuxt menetapkan *feature flag* [`__VUE_OPTIONS_API__`](https://vuejs.org/api/compile-time-flags#VUE_OPTIONS_API) milik Vue ke `false`. Ini membuat *runtime* Options API Vue tidak lagi dikompilasi ke dalam *bundle* klien.

#### Alasan Perubahan Ini

*Runtime* Options API selalu ikut terbawa di setiap *bundle* klien, padahal sebagian besar aplikasi Nuxt saat ini ditulis menggunakan Composition API dan `<script setup>`. Dengan membuangnya, ukuran *bundle* klien jadi menyusut (sekitar 6 kB setelah di-minify / 2 kB saat di-gzip pada aplikasi minimal).

#### Langkah Migrasi

Kalau ada komponen kamu (atau komponen dari dependensi kamu) yang masih menggunakan Options API (seperti `export default { data() {}, methods: {}, ... }`), aktifkan kembali opsi ini di `nuxt.config` kamu:

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  vue: {
    optionsApi: true,
  },
})
```

::note
`defineNuxtComponent` tidak terpengaruh: opsi `asyncData` dan `head` di dalamnya ditangani melalui `setup()`, bukan melalui Vue Options API, jadi ia akan tetap berjalan baik apa pun keadaan *flag* ini.
::

### Halaman Bertipe (*Typed Pages*) Diaktifkan Secara Bawaan

🚦 **Tingkat Dampak**: Minimal

#### Apa yang Berubah

Dengan `compatibilityVersion: 5`, `experimental.typedPages` diaktifkan secara bawaan. Nuxt akan menghasilkan nama dan jalur rute yang bertipe dari direktori `pages/` milikmu, sehingga *composable* seperti `useRoute`, `navigateTo`, `<NuxtLink>`, dan `router.push` akan melalui pengecekan tipe berdasarkan rute asli yang kamu miliki.

#### Alasan Perubahan Ini

*Routing* bertipe bisa menangkap tautan yang rusak atau nama rute yang sudah tidak terpakai pada saat pengecekan tipe, bukan saat *runtime*. Selain itu, fitur ini sekarang sudah menjadi bawaan di `vue-router`, jadi sangat masuk akal untuk dijadikan pengaturan default.

#### Langkah Migrasi

Kalau kamu merujuk pada rute yang tidak ada (misalnya ada kesalahan ketik di prop `to`, atau rute yang didefinisikan secara dinamis di luar direktori `pages/`), pengecekan tipe sekarang akan menampilkan *error*. Perbaiki referensinya, atau perluas tipe rute yang dihasilkan untuk rute yang kamu tambahkan pada saat *runtime*.

::tip
Kamu bisa menguji fitur ini lebih awal dengan mengatur `future.compatibilityVersion: 5` (lihat bagian [Pengujian Nuxt 5](/docs/4.x/getting-started/upgrade#testing-nuxt-5)) atau dengan mengaktifkannya secara eksplisit melalui `experimental.typedPages: true`.
::

Sebagai alternatif lain, kamu bisa memilih untuk tidak mengikutinya dan kembali ke perilaku lama dengan:

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    typedPages: false,
  },
})
```

### `baseUrl` pada TypeScript Diabaikan

🚦 **Tingkat Dampak**: Minimal

#### Apa yang Berubah

Dengan `compatibilityVersion: 5`, Nuxt menghapus `compilerOptions.baseUrl` dari konfigurasi TypeScript yang dihasilkannya. *Alias* relatif untuk Nuxt dan Nitro sekarang diselesaikan langsung dari direktori *build* Nuxt, alih-alih menggunakan `baseUrl` kustom.

#### Alasan Perubahan Ini

TypeScript 6 sudah mendeklarasikan `baseUrl` sebagai usang (*deprecated*), dan opsi ini sebenarnya tidak lagi diperlukan saat kita menggunakan `paths`. Penghapusan opsi ini juga menjaga *alias* yang dihasilkan Nuxt tetap terpatok secara konsisten pada konfigurasi yang memuatnya.

#### Langkah Migrasi

Hapus `baseUrl` dari konfigurasi TypeScript Nuxt kamu. Kalau kamu menggunakannya untuk mempatok *alias* Nuxt atau Nitro yang relatif, ubahlah *alias* tersebut menjadi jalur yang absolut:

```diff [nuxt.config.ts]
+ import { fileURLToPath } from 'node:url'
+
  export default defineNuxtConfig({
    alias: {
-     images: './assets/images',
+     images: fileURLToPath(new URL('./assets/images', import.meta.url)),
    },
-   typescript: {
-     tsConfig: {
-       compilerOptions: {
-         baseUrl: '..',
-       },
-     },
-   },
  })
```
