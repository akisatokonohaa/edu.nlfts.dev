Nuxt memakai dua direktori berbeda untuk menangani aset seperti *stylesheet*, *font*, atau gambar.

- Konten di dalam direktori [`public/`](/nuxt/directory-structure/public) akan disajikan apa adanya di akar *server*.
- Secara konvensi, direktori [`app/assets/`](/nuxt/directory-structure/app/assets) dipakai untuk menyimpan setiap aset yang ingin kamu proses melalui *build tool* (Vite atau webpack).

## Direktori Public

Direktori [`public/`](/nuxt/directory-structure/public) berfungsi sebagai *public server* untuk aset statis yang bisa diakses publik melalui URL tertentu di aplikasimu.

Kamu bisa mengakses file yang ada di direktori [`public/`](/nuxt/directory-structure/public) ini, baik melalui kode aplikasimu maupun langsung dari peramban, dengan menggunakan URL akar yaitu `/`.

### Contoh

Misalnya, kamu mau mereferensikan file gambar yang ada di direktori `public/img/`. Gambar tersebut bisa diakses melalui URL statis `/img/nuxt.png`:

```vue [app/app.vue]
<template>
  <img
    src="/img/nuxt.png"
    alt="Discover Nuxt"
  >
</template>
```

## Direktori Assets

Nuxt memakai [Vite](https://vite.dev/guide/assets) (secara bawaan) atau [webpack](https://webpack.js.org/guides/asset-management/) untuk membangun dan meng-*bundle* aplikasimu. Fungsi utama dari *build tool* ini sebenarnya adalah memproses file JavaScript, tapi fungsinya bisa diperluas melalui *plugin* (untuk Vite) atau *loader* (untuk webpack) agar bisa memproses jenis aset lainnya, seperti *stylesheet*, *font*, atau SVG. Tahap ini akan mengubah file aslinya, yang tujuannya utamanya untuk performa atau *caching* (misalnya seperti *minifikasi stylesheet* atau *cache invalidation* di peramban).

Berdasarkan konvensi, Nuxt memakai direktori [`app/assets/`](/nuxt/directory-structure/app/assets) untuk menyimpan file-file ini. Namun, tidak ada fitur *auto-scan* untuk direktori ini, dan kamu sebenarnya bebas menggunakan nama lain jika mau.

Di dalam kode aplikasimu, kamu bisa mereferensikan file yang ada di direktori [`app/assets/`](/nuxt/directory-structure/app/assets) dengan menggunakan path `~/assets/`.

### Contoh

Misalnya, kamu mau mereferensikan file gambar yang nantinya akan diproses kalau *build tool*-nya sudah dikonfigurasi untuk menangani ekstensi file tersebut:

```vue [app/app.vue]
<template>
  <img
    src="~/assets/img/nuxt.png"
    alt="Discover Nuxt"
  >
</template>
```

::note
Nuxt tidak akan menyajikan file yang ada di direktori [`app/assets/`](/nuxt/directory-structure/app/assets) dalam bentuk URL statis seperti `/assets/my-file.png`. Kalau kamu membutuhkan URL statis, pakailah direktori [`public/`](/nuxt/getting-started/assets#public-directory).
::

### `src` Statis vs. Dinamis

Ketika `src` berupa *string literal* statis di dalam *template*-mu, *build tool* akan menulis ulang path tersebut menjadi *runtime helper* yang bisa menemukan URL finalnya. Sebuah *path* publik seperti `/img/nuxt.png` akan dibungkus sehingga [`app.baseURL`](/nuxt/api/nuxt-config#baseurl)-mu otomatis diterapkan saat halaman di-*render*. Sementara itu, *path* yang di-*bundle* seperti `~/assets/img/nuxt.png` akan berubah menjadi *import* yang merujuk pada file output yang sudah di-*hash*.

```vue
<template>
  <!-- Path statis akan ditulis ulang: app.baseURL diterapkan saat runtime, dan file yang di-bundle akan di-hash. -->
  <img src="/img/nuxt.png">
  <img src="~/assets/img/nuxt.png">
</template>
```

Karena `app.baseURL` diterapkan saat *runtime*, *path* publik statis ini akan tetap berjalan meskipun *base URL*-nya baru diketahui saat proses *deploy* (misalnya diatur lewat `NUXT_APP_BASE_URL`). Cara ini juga bebas terserah file tersebut diproses oleh *build* atau tidak. Pengubahan path ini hanya akan terjadi pada *literal path* yang bisa dilihat oleh *build tool*.

Sebuah *binding* `:src` yang nilainya disusun saat *runtime* akan bersifat transparan (*opaque*) bagi *build tool*, jadi proses penulisan ulang tadi tidak akan terjadi. *String*-nya akan dipakai persis seperti yang kamu tulis:

```vue
<template>
  <!-- Ini tidak akan bekerja: path-nya dibangun saat runtime, jadi Vite tidak pernah melihatnya sebagai sebuah import. -->
  <img :src="`~/assets/img/${name}.png`">
</template>
```

Oleh karena itu, *path* publik yang dibangun saat *runtime* seperti `/img/${name}.png` **tidak** akan otomatis diberi awalan [`app.baseURL`](/nuxt/api/nuxt-config#baseurl). Kalau aplikasimu di-*deploy* di bawah akar *origin* (misalnya di sub-direktori), kamu harus menambahkan awalannya sendiri menggunakan [`useRuntimeConfig().app.baseURL`](/nuxt/api/composables/use-runtime-config) (bisa memakai bantuan [`joinURL`](https://github.com/unjs/ufo#joinurl) misalnya).

Bagian di bawah ini akan menjelaskan cara menangani setiap kondisi ketika *path*-nya baru diketahui saat *runtime*.

#### Aset Publik (*Public Assets*)

Kalau file-file tersebut tidak perlu diproses atau di-*hash*, taruh saja di direktori [`public/`](/nuxt/directory-structure/public) lalu referensikan memakai URL-nya:

```vue [app/app.vue]
<script setup lang="ts">
const props = defineProps<{
  name: string
}>()

const imageUrl = computed(() => `/img/${props.name}.png`)
</script>

<template>
  <img
    :src="imageUrl"
    :alt="props.name"
  >
</template>
```

File yang ada di dalam `public/` akan mempertahankan nama file aslinya.

#### Aset yang Di-*bundle* dengan Vite

Pendekatan di bawah ini secara khusus hanya berlaku untuk Vite, yang merupakan *builder* bawaan Nuxt.

Kalau kemungkinan file-nya sudah diketahui, sebutkan *import*-nya secara eksplisit:

```vue [app/app.vue]
<script setup lang="ts">
const props = defineProps<{
  theme: 'light' | 'dark'
}>()

const logos = {
  light: () => import('./assets/img/logo-light.png?url'),
  dark: () => import('./assets/img/logo-dark.png?url'),
}

const logoUrl = (await logos[props.theme]()).default
</script>

<template>
  <img
    :src="logoUrl"
    alt="Nuxt"
  >
</template>
```

Setiap *import* di sini punya *path* berupa *string literal*, sehingga Vite bisa menemukan kedua file tersebut saat proses *build*, sambil tetap hanya memuat modul yang terpilih saat *runtime*.

Kalau ada banyak file yang berada di direktori dan ekstensi yang sama, gunakan *variable dynamic import* alih-alih menyebutkan file-nya satu per satu:

```ts
async function getImageUrl (name: string) {
  const image = await import(`./assets/img/${name}.png?url`)
  return image.default
}
```

Pada contoh di atas, hanya nama file saja yang boleh bersifat dinamis. Dengan membiarkan direktori dan ekstensi file tetap statis di dalam *import*, kamu membiarkan Vite menemukan file-file yang kemungkinan ada saat proses *build*.

Untuk pola yang lebih luas atau jika kamu butuh pemetaan (*map*) yang jelas dari file-file yang tersedia, gunakan `import.meta.glob`:

```ts
const images = import.meta.glob<string>('./assets/img/*.{png,jpg,svg}', {
  query: '?url',
  import: 'default',
})

async function getImageUrl (name: string) {
  const load = images[`./assets/img/${name}.png`]

  if (!load) {
    throw new Error(`Unknown image: ${name}`)
  }

  return await load()
}
```

Secara bawaan, *glob import* bersifat *lazy* (malas/diunduh saat dibutuhkan). Tambahkan `eager: true` kalau URL-nya harus tersedia secara sinkron:

```ts
const images = import.meta.glob<string>('./assets/img/*.{png,jpg,svg}', {
  query: '?url',
  import: 'default',
  eager: true,
})
```

Setiap aset yang cocok tetap akan disertakan di hasil *build*. *Lazy import* akan memuat setiap kecocokan sesuai permintaan (*on demand*), sementara *glob* yang bersifat *eager* akan memuat semua kecocokan di awal yang mana bisa meningkatkan ukuran JavaScript awal atau menambahkan aset-aset kecil secara *inline*.

::warning
Tunggulah (*await*) *lazy import* sampai selesai sebelum kamu memakai URL-nya di dalam *markup* yang di-*render* oleh server. Pola `new URL(..., import.meta.url)` milik Vite tidak akan bekerja dengan SSR.
::
